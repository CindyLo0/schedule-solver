Shift Coverage Solver

Weekly shift preferences for 8 people covering 24 hours a day, 7 days a week.

What this page is for

A team covers a 24-hour day with 8 nine-hour shifts, staggered 3 hours apart. Every person works 5 days and rests 2. This page captures each person's preference weights (0 to 100 points, higher meaning more wanted) and any hard personal constraints.

When the solver is run, it searches every possible assignment in this browser — there is no server and no precomputed answer. It then compares the result against each person's own ideal and against earlier runs, so the scores are about points earned and satisfaction, not about who got their one favourite. The same inputs always produce the same result, and nothing about the result is hidden or hardcoded.

How to check it yourself

  1. Change a weight below (for example, set one person's rest-day pair to 0).
  2. Run the solver and confirm the schedule, points and satisfaction change to reflect that edit.
  3. Change it back and confirm the original schedule returns.
  4. Look at the fairness view before and after a run: the running points and satisfaction for each person move, and the worst-off person is named plainly.
  5. Open the page source: scheduler.js holds the search and scoring, app.js holds this interface. Both are plain, readable JavaScript.

People and preferences

Give each rest-day pair and each shift slot a weight from 0 to 100; higher means more wanted. Blank or out-of-range values count as 0, and the running total for each dimension is shown next to it. The highlighted priority is the dimension a person cares about most.

Anyone with a no-work window is treated as indifferent by rule: both of their weight lists are flattened to equal values and their boxes are locked, because their window already decides which shift they can take.

All eight slots start at fixed times beginning 00:00.

Cross-run fairness

Every finished run is remembered in this browser. The fairness view works in points and satisfaction: each person has a running points total and a satisfaction percentage against their own ideal. The solver keeps its chosen total inside a fairness band, so it will give up a few points on purpose rather than leave one person far behind, and a breaker watches anyone who has been at the bottom for several runs.

Who's behind (before this run)

Sourced from the saved runs, lowest satisfaction first. Anyone near the bottom, or carrying a pending breaker, is marked.

Fairness ledger

Per person: satisfaction against their own ideal (recent runs weighted more heavily), cumulative points across all saved runs, and the points they earned in the most recent run. This lives in this browser only and is never uploaded.

Run the solver

The search runs exhaustively in this browser tab. The same preferences always produce the same schedule. Editing any preference and pressing Run again recomputes everything from scratch.
